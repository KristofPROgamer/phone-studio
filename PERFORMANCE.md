On 2026-10-01 the updated Android debug APK compiled, all 31 local unit tests passed, and lint reported no issues after small code/layout fixes and reviewed dependency/durability exceptions. All 27 notebook/source checks passed. The notebook, native GPU installer and phone app were not executed; no measured speed improvement or image-quality comparison is claimed. ## Pipeline understood before changes

1. **Tap:** `StudioViewModel.generate()` validates settings, resolves batch/backend seeds, persists request IDs, and starts `GenerationService`.
2. **Preflight and request:** `GenerationOrchestrator` runs enabled backends concurrently. Each `BackendRunner` checks `/phone-studio/health` and `/phone-studio/models`, builds the graph, and submits `/prompt` through HTTPS/ngrok Basic auth. The bridge also uses the Studio token. The request and prompt IDs support recovery of an ambiguous submission.
3. **Queue and loading:** a long-lived ComfyUI process accepts the graph. `CheckpointLoaderSimple` loads the selected checkpoint when needed; the bridge copies supported weights from Drive to a bounded local cache on first use. ComfyUI can cache node results and retain weights subject to memory pressure. A loader node in every graph does not imply a model reload on every request.
4. **Inference:** optional `LoraLoader`, positive/negative `CLIPTextEncode`, `EmptyLatentImage`, then `KSampler`. Existing defaults are one image per backend, 768 × 1024, 24 steps, CFG 6.5, `dpmpp_2m`/`karras`. The notebook already uses FP16 UNet/text, cuDNN autotune, channels-last, and PyTorch attention on T4.
5. **Post-processing/storage:** `VAEDecode` decodes the latent; ordinary `SaveImage` converts/encodes a PNG and writes it to the Drive-backed output directory. Encoding and durable storage remain on the critical path.
6. **Result response:** WebSocket events carry sampler progress/completion. `/history/{promptId}` remains authoritative and returns filenames/subfolders/types, not base64 image bodies. Polling remains a fallback.
7. **Phone image:** the app stores image metadata. Compose/Coil fetches authenticated binary `/view`, decodes and caches the image, then shows it. The original fresh-result display had a 180 ms crossfade, now disabled for Create results. A completed history record precedes the image download.

Startup is separate: install/update ComfyUI, mount Drive, resolve/download the default checkpoint, start the process, and run the notebook's two-step preview before opening the tunnel. A phone connection check can also enqueue a one-step warm-up at the selected shape.

Current changes to this original pipeline: ordinary app saves now stage the standard PNG locally and finish an unchanged-byte Drive copy before returning; recent `/view` requests can use local bytes. Startup warm-up matches the phone's 768 × 1024/default sampler. Following the latest speed-first instruction, implemented experimental cache/attention/precision options are requested on where supported. The saved phone switch controls per-render extras, while launch-time precision/compilation require a notebook restart. Balanced retains its recipe, not guaranteed previous pixels. Conditioning caching deliberately yields to EasyCache/T4 attention.

## Interface compatibility

No endpoint, authentication header, request ID or history/image descriptor field was removed or renamed. Additive phone parameters/image metadata record Extra acceleration, style weight and explicit negative-prompt presence with historical defaults. The optional `/prompt` extra-data flag and health capability are backwards compatible. Both sides must be updated for per-render switching; old apps use notebook defaults, old notebooks ignore the field. Launch-time precision/compile/newer-GPU attention need restart and are not disabled by the phone switch. The two presets share one standard graph; experimental defaults are now requested on, so image equivalence is not claimed. Editable legacy settings map to current recipes, while historical metadata and accepted batch parameters are not rewritten. Fast PNG is lossless but changes compressed bytes and adds its actual encoding record.

Optional `FAST_T4_FLASH_ATTENTION` requires only notebook edits. It attaches a guarded SDXL model hook rather than changing the phone's graph or endpoints. The notebook includes pinned installer/adapter source; no additional source upload is required. Installation occurs only when enabled, in isolated local storage, with at most two compile jobs, a 600-second compile limit, host-RAM/disk guards and three tiny numeric/current-stream checks. Installed PyTorch/CUDA are preserved. Unsupported setup/calls use the existing SDPA path; native CUDA failures propagate. The option changes arithmetic. The saved phone switch records its per-render selection, but exact image reuse also requires the same notebook flags and validated runtime build. Enable, comparison and reversal details are in [T4 Fast attention](SPEED_MODES.md#fast-t4-flashattention). No build, preflight, full-image comparison or measured speedup was performed here.

The first coordinated addition is optional `GET /phone-studio/models?cached=1`:

- **Notebook:** bridge `model_catalog`, `phone_studio_models`, download invalidation, plus `MODEL_CATALOG_CACHE_SECONDS` in the GPU settings and subprocess environment.
- **Phone:** `ComfyApi.listModels(allowCached = true)` used only by `BackendRunner.probe`. All other callers request a fresh catalog.

An old app receives fresh catalogs from the updated notebook. The old notebook ignores the new query parameter and still returns its normal catalog to the new app. The optimization benefits from updating both sides; the existing wire interface remains usable in either order. Copies/moves/deletions made directly in Drive can leave preflight stale for at most five minutes; explicit Refresh updates it immediately. Successful in-app downloads invalidate it. A stale entry never substitutes a different checkpoint.

Startup-warm-up reuse also benefits from updating both sides: notebook launch/bridge cells publish optional instance-bound `completedWarmup` in the existing health response; `ComfyApi.ServerHealth` decodes it and `StudioViewModel` matches settings before skipping its preview. Older apps ignore the field; older notebooks omit it, preserving ordinary app warm-up. No endpoint or generation schema changed. Metadata is invalidated by subsequent workflow submission; it does not promise continued GPU residency.

### How to interpret the logs

- Colab: `queue_wait` is enqueue to execution start; `checkpoint_load`, `lora_load`, each `text_encode`, `sampling`, `vae_decode`, and `save_png_drive` are node wall times with GPU synchronization before/after. Startup/app warm-up logs have `warmup: true` and write local `save_png_preview` output.
- `model_cache_lookup_copy` is nested inside loading; do not add it again to stage totals. GPU transfers/offload performed inside a node belong to that node. `save_png_drive` remains the outer save timer; staged saves add nested `save_png_local` (conversion/encoding/local I/O) and `save_png_drive_copy` (unchanged bytes/durable copy), plus `view_local_read` on cache hits. Do not add nested times again. The outer timer also covers synchronization/maintenance/descriptor work.
- With local staging, `png_output` carries `encoded_bytes`, `image_count` and the actual `compress_level`. Its `ms: 0` is diagnostic metadata, not a timed stage. Use it to detect when an encoding-time saving is offset by a bigger Drive/network payload.
- GPU stages include `gpu_memory_before`/`gpu_memory_after`: allocated, reserved, device-free/total MiB and allocator peak. These are boundary samples, not per-step transfer traces; the peak is cumulative since the allocator's last reset and this diagnostic does not reset it. Low free memory alone is not proof of unnecessary offloading, especially with ComfyUI dynamic VRAM.
- `execute_total` includes graph/cache/other execution overhead. `queued_to_execute_end` also includes queue wait and carries the executor success flag. Cached/not-executed nodes produce no stage log; absence does not mean a measured zero.
- `http_models`, `http_prompt`, `http_view_handler_only` measure server handler time only. In particular the `/view` handler returns a file response before the full transfer, so that timer is **not** image-download duration. HTTP lines do not carry per-render correlation; use one backend/request for initial diagnosis.
- Phone: `accepted`, `probe_complete`, `submitted`, `history_ready`, `image_ready` carry request/prompt IDs and monotonic `elapsed_ms` plus `since_previous_ms`. `history_ready` is tap-to-result-metadata round trip; `image_ready` is tap-to-Coil-decoded-bitmap readiness, before presentation. Fresh Create results no longer add a fade. Their difference includes UI scheduling, file transfer and decode, not just network time.
- `origin=resume` explicitly starts at recovery, because a restarted process has no original monotonic tap clock. Do not mix resumed timings with `origin=tap`. Image timing is currently attached to the Create result card; if it is offscreen, the app is backgrounded, or you only open Library, that end-to-end sample is delayed or absent. Failed/cancelled requests may have only partial traces.
- Timings on separate devices use independent monotonic clocks. Join by request/prompt IDs and compare durations, not absolute timestamps. Logs deliberately omit prompts, URLs, image data, headers and credentials.

## Not changed and remaining limits

- SaveImage still completes durable Drive originals synchronously; its standard encoder can now write locally before copying identical bytes. No asynchronous durability or resizing was introduced. Requested-on lossless Fast PNG trades encoding cost for file size. Balanced keeps its sampling recipe; requested-on cache/attention/precision experiments can change pixels and make no quality-equivalence claim.
- Existing FP16 UNet/text, channels-last, cuDNN autotuning and GPU-dependent attention selection were preserved; supported-newer-GPU compilation is now requested by default, still disabled on T4. They are pre-existing settings, not new quality-neutral claims. No new paid packages or services were added.
- Matching completed startup work is now reused, with a per-backend in-flight guard and sampler/scheduler in the app signature. Other app previews still mark their signature after submission acceptance, not confirmed completion; a failed accepted preview can therefore remain recorded for that runtime. CFG-1/LoRA/mismatched workflows keep their existing preview path.
- Forced `highvram`, TensorRT, T4 model compilation and additional model replicas remain outside the default path. A version-checked legacy memory experiment and guarded T4 attention extension are available as optional settings. The extension's bounded build adds startup time and has unmeasured whole-image benefit; tiny preflights do not establish final-image quality. TensorRT remains deferred. Baseline remains T4 with automatic VRAM management, existing 24 GiB model disk cache and 8 GiB disk reserve; actual hardware/space availability is controlled by Colab. See GPU research for source findings.
- WebSocket failure now restores fallback polling; it does not add an automatic socket reconnection loop. Stop still ends phone monitoring, not necessarily server execution. Runtime restart still loses the in-memory recovery map/history. No cross-runtime exactly-once guarantee is claimed.
- Read-only HTTP calls now cancel promptly at coroutine cancellation; terminal socket events can interrupt one stalled history GET. Each result still comes from fresh authoritative history. Mutating POST calls keep the existing blocking transport, no-replay behavior and ambiguous-submit recovery. Stop does not promise cancellation of an accepted server render.
- ComfyUI is updated from its latest branch at notebook startup. Diagnostic wrappers depend on the current standard node/executor API, checked against the upstream [nodes](https://github.com/Comfy-Org/ComfyUI/blob/master/nodes.py) and [execution](https://github.com/Comfy-Org/ComfyUI/blob/master/execution.py) sources. Missing signatures are reported where guarded; a future incompatible version still needs review. Disable diagnostics and restart if hooks fail.
- Colab resources and free-tier duration are not guaranteed. The official [Colab FAQ](https://research.google.com/colaboratory/faq.html) warns that bypassing the notebook UI for external content-generation interfaces commonly causes termination on free runtimes. This existing phone-controlled architecture cannot guarantee uninterrupted free-tier use. Its monitoring loop cannot bypass reclamation; no keepalive evasion or paid upgrade was added.
- A noticeable overall improvement remains unverified. If `sampling` dominates and preflight/display are already short, the quality-preserving changes may produce only a modest end-to-end improvement. Optional sampling/kernel changes were implemented from source inspection without waiting for runtime logs; the comparison instructions describe how to assess their actual speed and image effects.
