# T4 GPU acceleration research

Updated on 2026-10-01. This is source research, not a GPU benchmark of Phone Studio. The Colab notebook, native T4 kernel and diagnostic probe have not been run here. Published kernel/build numbers below belong to their authors and do not predict this app's elapsed time. Local Android build checks, where reported separately, do not verify generation speed. The notebook updates ComfyUI at startup, so record the actual runtime versions before comparing.

At the user's request, implemented speed experiments are now requested **on by default**, with hardware/API checks and fallbacks. This replaces the earlier quality-preserving default policy: EasyCache and lower-precision arithmetic can change the generated image. The phone has exactly two presets, Balanced 24 and Fast 18, and a saved **Extra acceleration** switch, on by default. That switch gates per-request EasyCache, T4 attention, lossless PNG tuning and eligible conditioning caching. It does not undo launch-time precision, compilation or the newer-GPU attention choice; those require notebook settings and a backend restart. `VRAM_MODE = 'auto'` remains the default because memory modes are mutually exclusive; diagnostic timing remains off because synchronization adds overhead. [Settings and verification](SPEED_MODES.md)

## What this notebook already does

The intended baseline is NVIDIA T4 (Turing, SM7.5, 16 GB nominal memory). FP16 Tensor Cores are available; native Ampere TF32/BF16 and newer FP8 paths are not equivalent upgrades for this GPU. The existing notebook selects FP16 diffusion/text, PyTorch SDPA, channels-last and named cuDNN autotuning. A persistent ComfyUI process, graph/model caching and bounded local checkpoint copies already exist. These are not newly discovered missing optimizations. [NVIDIA T4 specifications](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/tesla-t4/t4-tensor-core-datasheet-951643.pdf), [Turing architecture](https://www.nvidia.com/content/dam/en-zz/Solutions/design-visualization/technologies/turing-architecture/NVIDIA-Turing-Architecture-Whitepaper.pdf)

Current ComfyUI enables two asynchronous weight-offload streams and pinned host memory by default on NVIDIA. Re-adding those flags provides no demonstrated improvement. Its dynamic VRAM startup depends on the installed PyTorch, AIMDO initialization and selected mode; the actual startup log can report a fallback. A normal loader node in each graph does not establish that weights are reloaded each time. [Offloading/pinning source](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py), [startup selection](https://github.com/Comfy-Org/ComfyUI/blob/master/main.py)

## Attention: SDPA, xFormers and T4 FlashAttention

ComfyUI's SDPA path reshapes/transposes Q/K/V and calls PyTorch's scaled-dot-product attention. PyTorch chooses a supported backend based on version, device, dtype, shape and mask. A T4 can use memory-efficient attention; forcing mainstream FlashAttention is not a general T4 remedy. Installing xFormers also does not guarantee a faster path than the existing fused SDPA kernel, and an unmatched wheel can replace the notebook's PyTorch/CUDA packages. The enabled T4 setting instead attempts to build an isolated private extension on eligible hardware, preserving the installed Torch/CUDA packages. [ComfyUI attention implementation](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/ldm/modules/attention.py), [PyTorch SDPA selection](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html), [xFormers operators](https://facebookresearch.github.io/xformers/components/ops.html)

The official FlashAttention repository identifies mainstream FA2 with Ampere/Ada/Hopper and links a separate Turing implementation. That distinction matters: the notebook's T4 is SM7.5. [Official FlashAttention support](https://github.com/Dao-AILab/flash-attention#nvidia-cuda-support)

The [Turing implementation](https://github.com/ssiu/flash-attention-turing) supports head widths 64/96/128, unequal Q/K sequence lengths and noncausal attention, so ordinary SDXL self/cross attention is a plausible target. Its README reports testing CUDA12.4 with PyTorch2.5.1/2.8.0; this is not a guarantee for the current Colab combination. Its “up to 2.19×” forward result is a kernel benchmark, not WAI/ComfyUI or tap-to-image timing.

Concrete requirements found in the upstream source, and addressed in the local guarded integration:

- ComfyUI's ordinary `--use-flash-attention` imports `flash_attn` with a different API. The local integration instead uses its per-model `optimized_attention_override`, preserving preferred attention functions and existing overrides. The stock PyTorch path remains the fallback.
- The upstream C++ binding interprets tensor data as FP16 without a protective dtype check. Both local bridge and patched binding require CUDA FP16/SM7.5 and head width 64; masks, other dtypes, training/tracing and unsupported shapes use the original implementation.
- The kernel assumes contiguous B,L,H,D storage. The adapter establishes full contiguous layout and 16-byte alignment, without dtype casts. Copies are part of the cost and can offset kernel gains.
- The upstream launch does not pass PyTorch's current CUDA stream. The pinned patch adds current-stream launch, a device guard and checked launch errors. Three tiny numeric/stream checks run automatically **when the user runs the enabled installer**, including unequal lengths and partial blocks. They have not been executed here.
- Fast-math and floating-point order still differ. This option is requested on by default; mathematical equivalence and a tiny numeric check cannot prove identical pixels or full-image quality.

Sources: [Python API](https://github.com/ssiu/flash-attention-turing/blob/main/flash_attention_interface.py), [binding/kernel source tree](https://github.com/ssiu/flash-attention-turing/tree/main/csrc), [build configuration](https://github.com/ssiu/flash-attention-turing/blob/main/setup.py). The guarded adapter is implemented and requested by the notebook defaults. Compilation, runtime correctness, full-image comparisons and any speed claim still require a real Colab run.

For perspective, if attention were 40% of render time and became twice as fast, the overall render would become 1 / (0.6 + 0.4 / 2) = 1.25× as fast. This is an illustrative calculation, not this app's attention share. Loading, convolutions, VAE, saving and transfer remain.

## Optional T4 build and integration

`FAST_T4_FLASH_ATTENTION = True` is already the notebook default. On an existing session, stop the launch cell, rerun GPU settings and the bridge-writing cell, then restart the launch cell. Uploading the notebook alone is sufficient: installer and adapter source are embedded. A failure during setup keeps the existing attention choice and prints a reason. On non-SM7.5 hardware this option is skipped without replacing the existing GPU-specific attention selection.

The installer pins Turing source revision `9ef98fcb506bb1e2fe3cece50935e2935bf6b124` and its CUTLASS revision, verifies the files it patches, and compiles only the noncausal head-64 forward specialization. It uses a private module under `/content/phone_studio_t4_flash/`, leaving installed Torch/CUDA and ComfyUI source intact. CUDA12 Torch and a matching CUDA-major compiler are required; no replacement compiler/runtime is downloaded. Missing free build helpers can be installed into this private directory with `--no-deps`.

Compilation is capped at two jobs and 600 seconds for the build command; source/dependency downloads and checks add separate time. The installer requires at least 4 GiB available host memory and the existing disk reserve plus 2 GiB scratch. These guards reduce resource demand; they do not guarantee a build will fit or that Colab will supply a T4. A validated build can be reused within a matching runtime, after repeating its tiny checks. It does not persist across runtime resets.

Before enabling the hook, the bridge checks manifest/binary hashes, Python/Torch/CUDA identity, required preflight evidence and ComfyUI's attention API. Only detected ordinary SDXL diffusion models receive the hook through a shared-weight clone; CLIP/VAE and phone graphs stay unchanged. The bridge refuses to displace preferred/quantized kernels or existing overrides. Eligible unmasked FP16 head-64 inference uses the new kernel; unsupported calls retain SDPA. A native CUDA execution failure is allowed to fail the render rather than retry on a potentially invalid CUDA context.

One-line verification: after restarting with the setting enabled and phone Extra acceleration on, an eligible SDXL render should print `T4 FlashAttention used for eligible SDXL FP16 head-64 attention`; compare synchronized `sampling` and phone `image_ready` durations with equal warm-up, fixed seed sequence and all other Fast settings off. `hook enabled` alone does not prove a call used it. New phone image metadata records the per-request switch, not the notebook settings, build identity or actual kernel dispatch; record those separately.

One-line reversal: set `FAST_T4_FLASH_ATTENTION = False`, rerun settings/bridge and restart ComfyUI; a native failure may require a fresh runtime. The standalone source files are `tools/t4_flash_attention_install.py` and `tools/t4_flash_attention_bridge.py`; changing them requires replacing their embedded notebook copies too. Copies of the notebook/docs/probe immediately before this addition are in `.work-speed/t4-flash-original/`.

## Memory and precision settings added

`VRAM_MODE = 'legacy'` adds only `--disable-dynamic-vram`, preserving ordinary smart-memory behavior. The launch cell checks the installed CLI source for support and gives a clear error if removed. ComfyUI currently warns this option may disappear. Compare against `'auto'`; neither mode is declared faster. `'high'` remains a separate existing full-residency experiment. [CLI options and mode behavior](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/cli_args.py)

`FAST_FP16_ACCUMULATION = True` is the default and adds only the named `fp16_accumulation` feature beside `autotune`, with CLI/PyTorch availability checks. Do not use bare `--fast`: current ComfyUI interprets it as all fast features, including unrelated precision changes. Confirm the server logs “Enabled fp16 accumulation” when testing; unsupported flags print a skip reason and retain the supported path. This setting is global to the backend, is not stored in phone generation metadata, and must be repeated to reproduce a comparison. [Feature implementation](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py)

PyTorch documents full FP16 accumulation on SM7.0+ with reduced numerical precision and increased overflow likelihood. It differs from existing FP16 weights and from selective reduced-precision reductions. The user's speed-first default requests it on, without demonstrated quality equivalence or elapsed savings; non-finite/black output is a failed experiment. Set it to False and restart to compare the original arithmetic. [PyTorch full FP16 accumulation](https://docs.pytorch.org/docs/stable/notes/cuda.html#full-fp16-accumulation-in-fp16-gemms)

With `PHONE_STUDIO_TIMING = True`, GPU stage logs now include allocated/reserved/device-free memory before and after each stage. These snapshots cannot prove per-step transfer frequency; the allocator peak is cumulative since its last reset, which this instrumentation does not change. Dynamic VRAM may own reusable memory beyond PyTorch's allocator view, so low reported free memory alone is not an offload diagnosis. Verify by checking the fields on a real `sampling` log; disable timing and restart to remove all diagnostic overhead.

Do not default to `--gpu-only`, `--high-ram`, enlarged model/result caches, or forcing `--fast-disk`. These can increase GPU/host memory demand or bypass storage detection. Current ComfyUI reports its detected storage policy; local Colab storage and mounted Drive are not assumed to have identical NVMe behavior. [Storage-policy source](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/storage.py)

## TensorRT: possible hardware, unsuitable install-only shortcut

T4 is hardware-eligible: current NVIDIA requirements still include Turing/SM7.5. Package/CUDA matching is a separate question; current default `tensorrt` packaging targets CUDA13, with a CUDA12 variant available. [NVIDIA prerequisites](https://docs.nvidia.com/deeplearning/tensorrt/latest/installing-tensorrt/prerequisites.html), [support matrix](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html)

The unused notebook TensorRT installer has been removed during the two-preset cleanup; this remains background research. Its upstream requirements specify `tensorrt>=10.0.1` without an upper bound, while the inspected converter still calls `BuilderFlag.FP16`, removed in TensorRT11. A latest install can therefore be incompatible. Conversion also asks ComfyUI to force-patch/full-load weights, which the current dynamic model patcher rejects. A compatible version set and dedicated conversion memory mode must be established first. [Requirements](https://github.com/comfyanonymous/ComfyUI_TensorRT/blob/master/requirements.txt), [converter](https://github.com/comfyanonymous/ComfyUI_TensorRT/blob/master/tensorrt_convert.py), [TensorRT11 removed Python APIs](https://docs.nvidia.com/deeplearning/tensorrt/latest/api/migration/tensorrt-10x-to-11x-python-api-reference.html), [dynamic patcher](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_patcher.py)

Upstream describes SDXL support, a recommendation of at least 12 GB GPU memory, image-engine builds around 3–10 minutes, and no runtime LoRA/ControlNet support in those engines. These are upstream descriptions, not this runtime's results. T4's nominal capacity does not establish sufficient build/activation memory. Static engines constrain shape/batch; wide dynamic ranges can need more memory. [TensorRT node documentation](https://github.com/comfyanonymous/ComfyUI_TensorRT)

Installing that node cannot accelerate the phone's unchanged `CheckpointLoaderSimple` graph. A future implementation would need notebook engine conversion/loader support **and** app workflow selection, original CLIP/VAE wiring and model/engine/shape validation. That would conflict with this stage's single standard workflow unless the design changes. Engines also have runtime/hardware compatibility limits and possible numerical differences. [Loader](https://github.com/comfyanonymous/ComfyUI_TensorRT/blob/master/tensorrt_loader.py), [engine compatibility](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html), [accuracy](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/accuracy-considerations.html)

## Compilation and VAE precision

Current Triton lists NVIDIA SM8.0+ support. The notebook skips its normal Inductor/Triton compilation path on T4 and pre-Ampere hardware, even though `PHONE_STUDIO_AUTO_COMPILE` now defaults to `1` on eligible newer GPUs. Set that Colab Secret to `0` and restart to disable compilation. Compilation can increase startup/first-use time, and an enabled setting is not proof that a faster kernel was used. This does not mean every possible `torch.compile` backend is unsupported on T4, but an eager backend is not a substitute for those GPU kernel fusions. No T4 compiler package or CUDA-graph patch was added. [Triton compatibility](https://github.com/triton-lang/triton#compatibility)

VAE dtype is chosen separately from `--fp16-unet`/text and depends on model-supported dtypes. The SDXL AutoencoderKL branch retains BF16/FP32 candidates; T4 lacks the ordinary BF16 selection, so FP32 is the inferred baseline before this experiment. `FAST_FP16_VAE = True` now requests the stock forced-FP16 path by default, subject to CLI support. It can change output or produce non-finite/black images. Set it to False and restart to use the ordinary dtype choice. VAE replacement/approximate decoding remain deferred because they change model components and need another recipe. [VAE/model loading](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/sd.py), [dtype choice](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py)

`FAST_FP16_INTERMEDIATES = True` requests another stock option by default. This changes selected CPU latent/output buffers, not all denoiser activations: seeded FP32 noise is rounded to the FP16 latent dtype before the sampler casts noise/latent back to FP32, and decoded RGB reaches output processing in FP16. A portrait RGB buffer shrinks from 9 to 4.5 MiB by shape/dtype calculation. Speed benefit is unknown and may be negligible; pixel differences are expected. Set it to False and restart for the ordinary buffer dtype. [Noise creation](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/sample.py), [sampling](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/samplers.py), [intermediate dtype](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py)

## Render-local conditioning cache

The ordinary intermediate device is CPU; CLIP output/context batching can therefore lead to repeated CUDA context transfers in `BaseModel._apply_model`. A two-item 77-token, width-2048 FP16 context is approximately 616 KiB, calculated from shape/dtype rather than measured. This is not evidence that transfer dominates the render. [CLIP output placement](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/sd1_clip.py), [intermediate-device selection](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py), [context transfer](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_base.py)

`FAST_CONDITIONING_CACHE = True` requests the new `tools/conditioning_cache_bridge.py` hook. It caches stock cross-attention conditioning concatenation/padding and the usual FP16 CUDA transfer for the duration of one render. It does **not** cache attention K/V projections or change global conditioning classes. CPU snapshots isolate cached node outputs; keys include private tensor identity, shape/stride/dtype, destination device and CUDA stream. The total budget is 8 MiB including snapshots and retained GPU tensors, at most four layouts, with a 64 MiB free-memory margin. Conditions and buffers are restored/released in `finally`, including interrupted renders.

The hook is deliberately skipped when `PHONE_STUDIO_FAST_DENOISE_CACHE` or `PHONE_STUDIO_T4_FLASH_ATTENTION` is on in the server environment. The latter is passed as on only when the notebook T4 setting is enabled **and its build/preflight is available**. EasyCache is on by default, so conditioning caching normally reports a skip rather than operating simultaneously. If EasyCache is off and the T4 build fails, conditioning caching may remain eligible; a T4 build fallback alone does not enable it while EasyCache remains on. To compare it separately, set both `FAST_DENOISE_CACHE` and `FAST_T4_FLASH_ATTENTION` to False, rerun settings/bridge, and restart. The phone Extra acceleration switch must be on. Turning that phone switch off bypasses an installed hook; it does not install a hook that was skipped at server startup.

Eligibility is limited to inspected stock SDXL base/T4 FP16 behavior: batch one, CFG 6.5, DPM++ 2M with 18 or 24 steps, plain positive/negative text conditioning, stock progress callback and no compilation or custom hooks. Ordinary LoRA metadata is accepted; custom attachments, incompatible APIs/shapes/streams and insufficient memory retain the stock path. Extra retained tensors may affect CFG batching or offloading, so output equivalence and useful speed savings still need a real render comparison.

One-line verification: with other incompatible hooks disabled, a qualifying render should log `Conditioning cache released: hits=... misses=... retained_bytes=... cap_bytes=8388608`; compare synchronized sampling and total image-ready time using the same seed sequence and images. One-line reversal: set `FAST_CONDITIONING_CACHE = False`, rerun settings/bridge, and restart. The helper is embedded in the notebook; editing its standalone source also requires refreshing that embedded copy.

## Additional repeated work, left alone

SDXL cross-attention recomputes `to_k(context)`/`to_v(context)` on each model evaluation, before the attention hook. Ordinary phone prompt conditioning is fixed over the steps, but ComfyUI rebuilds batches with `torch.cat`, so tensor pointers are not a safe cache key. A per-render projection cache needs correct model/LoRA/conditioning invalidation, batch order and lifetime handling; extra GPU tensors can increase offloading. No reliable speed estimate or safe small default patch was established. [Attention projection](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/ldm/modules/attention.py), [conditioning concatenation](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/conds.py)

ComfyUI's optional cuBLAS extension was also inspected. At pinned `aredden/torch-cublas-hgemm` revision `4e8b688d4037878b67056721b1b7d27551742fed`, its **SIMT GEMV** source launches without PyTorch's current stream, computes the row grid using `(height + 1) / block_dim_y`, and truncates the vector loop through integer division. With the default 32 threads and width 320, the loop processes 256 entries by source calculation, leaving a tail unprocessed. These concerns are specific to that SIMT GEMV path; they do not establish that every cuBLAS GEMM path is incorrect. A bare optional flag does not repair this code or validate its compatibility with Colab's installed Torch. No cuBLAS extension was installed or enabled in this stage. [Pinned SIMT GEMV source](https://github.com/aredden/torch-cublas-hgemm/blob/4e8b688d4037878b67056721b1b7d27551742fed/src/simt_hgemv.cu)

The phone also waits for authoritative history metadata before fetching an image. Consuming pushed `executed` descriptors could save one metadata round trip, but needs completion validation and remains deferred. The phone transport now makes read-only GETs cancellable and races one terminal completion/error event against a stalled history read, followed by an authoritative fresh history fetch. This addresses the present read delay without trusting pushed image descriptors. Stable image-cache keys across tunnel changes could help old library loads and remain deferred.

An additional present post-processing cost was addressed separately: `FAST_PNG_COMPRESSION = True` selects lossless level 1 instead of stock level 4 by default for eligible phone saves, with the phone switch able to disable it per request. It can increase file/transfer size, so it is not a GPU speed claim. [Implementation and comparison](SPEED_MODES.md#fast-lossless-png)
